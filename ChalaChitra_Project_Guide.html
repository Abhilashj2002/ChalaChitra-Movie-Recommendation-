1. What is ChalaChitra?

An introduction to the application's purpose, users, and core functionality.

ChalaChitra is an intelligent movie discovery platform designed to help users find, track, and enjoy movies. The application combines modern web technologies with artificial intelligence to provide personalized recommendations and an interactive chatbot experience.

1.1 Core Purpose

The primary goal of ChalaChitra is to solve the "what should I watch?" problem. Users often spend more time browsing than actually watching content. This platform addresses that by:

  • Aggregating movie data from The Movie Database (TMDB)
  • Using AI to understand user preferences and queries
  • Maintaining a personal watch history and ratings
  • Providing intelligent recommendations based on mood, genre, and language preferences

1.2 Who Uses This Application?

Two Types of Users:

Regular Users: Can search movies, view details, maintain watch history, rate films, and interact with the AI chatbot for recommendations.

Administrators: Have all regular user capabilities plus access to system settings, user management, and feedback moderation.

1.3 System Architecture at a Glance

The application follows a three-tier architecture, which is a standard pattern for web applications. This separation allows each layer to be developed, maintained, and scaled independently.

Why This Architecture Works

The three-tier design provides several advantages. First, the Presentation Layer (React) focuses solely on user interface and experience, without worrying about data storage. Second, the Business Logic Layer (Express) handles all the rules—authentication checks, data validation, API orchestration—keeping these concerns centralized. Third, the Data Layer (SQLite) manages persistence, ensuring data survives even when the application restarts.

Key Benefit: If the frontend needs redesigning, the backend and database remain unchanged. If the database needs upgrading, only the data layer is affected. This modularity reduces risk and maintenance cost.

2. The Frontend: User Interface Layer

Understanding how users interact with the application and why React was chosen as the foundation.

2.1 Technology Choices Explained

The frontend is built using four core technologies, each serving a specific purpose in creating a fast, maintainable, and user-friendly interface.

React 19 - The UI Framework

React is a JavaScript library for building user interfaces using components. Think of components as Lego blocks—each piece (like a movie card or search bar) is self-contained and reusable across different pages. React 19 includes "Concurrent Features" that allow the interface to remain responsive even when loading data.

TypeScript - Type Safety

TypeScript adds type checking to JavaScript. Before the code runs, TypeScript verifies that functions receive the correct data types. This catches errors during development rather than after deployment, making the application more reliable.

Vite - Build Tool

Vite is a modern build tool that compiles the application for production. During development, it provides "Hot Module Replacement" (HMR), meaning changes appear instantly without full page reloads. This speeds up development significantly.

TailwindCSS - Styling

TailwindCSS is a utility-first CSS framework. Instead of writing custom CSS files, developers use predefined utility classes directly in the HTML. This approach ensures consistent styling across the application and reduces the amount of custom CSS that needs to be maintained.

The Caching Strategy

To avoid hitting API rate limits and improve performance, the application implements an in-memory caching system. When movie data is fetched, it's stored in the browser's memory (not localStorage) with an expiration time. Subsequent requests for the same data within the cache window return instantly without network calls.

Cache Durations Explained:

Trending Data: 10 minutes. Trends change frequently, so short cache.
Movie Details: 24 hours. Basic info (title, cast) rarely changes.
Search Results: 10 minutes. Searches might vary, but recent ones benefit from caching.
Video Links: 24 hours. Trailers and clips are relatively stable.

3.1 Express.js as the Foundation

The backend is built on Express.js, a minimalist web framework for Node.js. Express provides the infrastructure to receive HTTP requests from the frontend, process them, and return appropriate responses. It's lightweight by design—you add only the features you need.

Why Express Was Chosen

Express was selected over alternatives like Fastify or NestJS for several reasons:

  • Maturity: Express has been around since 2010 and is battle-tested at scale
  • Ecosystem: Thousands of middleware packages available for common tasks
  • Simplicity: The learning curve is gentle; code is straightforward to understand
  • Flexibility: No enforced architecture—you structure code as needed

3.2 CORS: Connecting Frontend to Backend

Modern web browsers enforce a security policy called "Same-Origin Policy." This means a webpage from one domain cannot make requests to a different domain by default. Since the frontend runs on port 3001 and the backend on port 3002, they are technically different origins.

3.4 The Authentication Process

When a user logs in, several steps ensure secure access:

  1. The user submits their email and password through the login form
  2. The frontend sends these credentials to the backend via a POST request
  3. The backend queries the database for a user with matching email and password
  4. If found, the backend returns user information (ID, username, role, preferences)
  5. The frontend stores this data in application state and redirects to the home page
  6. If not found, the backend returns a 401 Unauthorized error

SQL Injection Protection:

The backend uses parameterized queries where user input is treated as data, not executable code. This prevents attackers from injecting malicious SQL commands. For example, entering "' OR '1'='1" as a password would be treated as a literal string, not as a logic expression.

4. The Database: Data Persistence Layer

4.1 SQLite: The Serverless Database

Unlike traditional databases that require a separate server process (like MySQL or PostgreSQL), SQLite is serverless. The entire database exists as a single file on disk named cinema.db. This design choice significantly simplifies deployment and development.

Why SQLite Was Chosen

Advantages of SQLite for This Project:

Zero Configuration: No installation, no server to start, no users to create. The database file is created automatically on first run.

Single File: The entire database lives in one file, making backups as simple as copying a file.

Portability: The database works across Windows, macOS, and Linux without changes.

No Network Overhead: Since it's file-based, there's no network latency between application and database.

JSON Support: Modern SQLite versions can store and query JSON data, perfect for flexible schemas.

Trade-offs and Limitations

While SQLite is excellent for this project's scale, it has limitations:

  • Concurrency: SQLite handles multiple readers well but is limited with concurrent writes. For high-traffic production sites, a client-server database would be better.
  • Size: The in-memory nature (via sql.js) means the database size is limited by available RAM.
  • No User Management: Unlike PostgreSQL or MySQL, SQLite has no concept of database users and permissions.

Table Relationship Explanation

Each user in the Users table has a one-to-one relationship with User Preferences. This separation allows the user account structure to remain stable while preferences can evolve over time without database migrations.

The Watch History table has a one-to-many relationship with users—each user can have many watched movies. Importantly, when a movie is watched, a snapshot of the movie data is stored in this table. This means even if the movie is later removed from TMDB, the user still sees what they watched in their history.

The Ratings table is separate from history because a user might rate a movie they haven't marked as "watched" (perhaps they watched it elsewhere). The unique constraint on user_id + movie_id ensures each user can only rate a movie once.

4.3 The Hybrid JSON Approach

A unique aspect of this database design is the use of JSON strings within SQL tables. Rather than creating separate tables for genres, languages, and moods with complex join tables, these are stored as JSON arrays within the user_preferences table.

Why Store JSON in SQLite?

Simplicity: Instead of three junction tables (user_genres, user_languages, user_moods), we have one table with three JSON columns.

Flexibility: Adding a new preference type doesn't require database schema changes—just add a new JSON column.

Trade-off: We lose the ability to index and efficiently query individual array elements, but for this application's scale, the simplicity benefit outweighs this cost.

4.4 Data Integrity with Foreign Keys

The database uses foreign key constraints to maintain data integrity. When a user is deleted, the "ON DELETE CASCADE" rule automatically removes all their history, ratings, and preferences. This prevents orphaned records that would waste space and could cause errors.

5.2 Google Gemini AI

Google Gemini provides the artificial intelligence that powers the chatbot feature. When users type natural language queries like "I'm bored and want to watch something funny," Gemini interprets this intent and provides relevant responses.

Two-Stage Classification System

The application uses a hybrid approach that balances speed with intelligence:

┌─────────────────────────────────────────────────────────────────────────────┐ │ QUERY CLASSIFICATION PROCESS │ ├─────────────────────────────────────────────────────────────────────────────┤ │ │ │ User Input: "I want to watch an action movie" │ │ │ │ STAGE 1: Fast Local Classification (No API Call) │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ Keyword matching against known terms: │ │ │ │ │ │ │ │ "action" ──────► genre: action │ │ │ │ "horror" ──────► genre: horror │ │ │ │ "sad" ─────────► mood: sad │ │ │ │ "Tom Cruise" ──► actor: Tom Cruise │ │ │ │ "Inception" ───► movie: Inception │ │ │ │ │ │ │ │ Result: { type: "genre", entity: "action", confidence: 0.9 } │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ │ ┌────────────────────────┴────────────────────────┐ │ │ │ Low Confidence (below 0.7) │ High Confidence │ │ ▼ ▼ │ │ STAGE 2: AI Classification (API Call) Use Local Result │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ Send query to Google Gemini API │ │ │ │ Model: gemini-1.5-flash │ │ │ │ Temperature: 0.1 (consistent, not creative) │ │ │ │ │ │ │ │ Response: JSON with type, entity, confidence │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ │ FALLBACK: If API fails or no key configured │ │ ┌─────────────────────────────────────────────────────────────────────┐ │ │ │ Return best guess from local classification │ │ │ │ or default to "general" type for safe response │ │ │ └─────────────────────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────────────────┘

Why Two Stages?

Cost and Performance:

Every call to the Gemini API costs money and adds latency (200-500ms). By handling common queries locally, we save costs and provide instant responses. The AI is reserved for ambiguous or complex queries where keyword matching fails.

Intent Types and Actions

Once a query is classified, the application takes different actions based on the intent type:

  • Genre Intent: Query TMDB's discover endpoint with genre filter
  • Mood Intent: Map mood to genres (e.g., "sad" → drama, "excited" → action), then fetch movies
  • Actor Intent: Use TMDB's person search, then fetch their filmography
  • Movie Intent: Search TMDB for the specific movie title
  • General Intent: Use Gemini to generate a conversational response

6.2 Key Architectural Decisions

Decision 1: In-Memory Caching with Map

Using JavaScript's Map data structure for caching instead of localStorage or IndexedDB provides O(1) lookup time and automatic expiration handling. The trade-off is that cache is lost on page refresh, but this is acceptable given the 10-minute expiry windows.
Decision 2: Hybrid JSON in SQLite

Storing arrays (genres, languages) as JSON strings simplifies the schema and reduces table count. This works because these arrays are small and don't require complex querying. For larger datasets, a normalized approach with junction tables would be more appropriate.
Decision 3: Two-Stage AI Classification

The combination of local keyword matching and cloud AI provides both speed and intelligence. Local handling covers 80% of common queries instantly, while AI handles the remaining 20% that require natural language understanding.

6.3 Advantages of This Architecture

Development Speed

The chosen stack prioritizes developer productivity. React's component model, Tailwind's utility classes, and Vite's fast feedback loop allow features to be built quickly. SQLite eliminates database setup time entirely.

Operational Simplicity

With SQLite, there's no separate database server to monitor, backup, or scale. The entire backend can be deployed as a single Node.js application. This reduces operational overhead significantly.

User Experience

The caching strategy ensures pages load quickly. The fallback mechanisms (localStorage when backend is down, local classification when AI is unavailable) provide graceful degradation rather than hard failures.
